# Supply chain, scanning, runtime, and service-mesh mTLS

The two ends of the container lifecycle: what enters the cluster (image scanning and supply-chain integrity) and what happens once a workload runs (runtime protection and service-mesh mTLS). Load this for scanning gates, SLSA and cosign, SBOMs, seccomp and AppArmor, and mesh identity. The cluster-hardening controls in between (admission, RBAC, network policy) live in `concepts.md`.

## Build-phase hygiene

Everything downstream is easier when the image is small and clean to begin with:

- Choose a minimal base (distroless, scratch, Alpine) to shrink the attack surface.
- Pin to a digest, not a mutable tag: `FROM ubuntu@sha256:...` rather than `:latest`.
- Pull only from trusted registries with content trust enabled.
- Run as a non-root user and drop capabilities at build time where the base allows.
- Never bake a secret into an image layer. Even a secret deleted in a later layer persists in history. Use a build-time secret mount, and inject runtime secrets through the cluster (see the secrets patterns below).

## Image scanning

### How a scanner works

An image scanner extracts the OCI image layers (ordered tar archives), reads each layer's filesystem, and reads the package databases it finds: `/var/lib/dpkg/status` (Debian/Ubuntu), `/var/lib/rpm/Packages` (RHEL family), `/lib/apk/db/installed` (Alpine), and language manifests such as `package-lock.json`, `pom.xml`, or a Python `dist-packages` tree. It then matches package names and versions against CVE databases and reports fix availability. A good scan covers OS-package CVEs, language-library CVEs, hardcoded secrets, misconfigurations (running as root, granted capabilities, SUID binaries), licence obligations, and known-malicious binaries.

Tooling spans open source and commercial (Trivy, Grype, Snyk Container, and the scanners bundled into cloud and CNAPP platforms). The methodology is what matters; the tool is interchangeable.

### Prioritising the findings

Raw CVSS alone over-fills the queue, because technical severity and real-world exploitation are weakly correlated. Order the work by decisiveness:

1. **CISA KEV (Known Exploited Vulnerabilities)**: actively exploited in the wild; fix immediately regardless of CVSS.
2. **CVSS 9.0 and above with a public exploit**: high severity and weaponised; fix within 24 to 48 hours.
3. **CVSS 7.0 to 8.9 with a public exploit**: fix within days.
4. **CVSS 9.0 and above without a known exploit**: fix within one to two weeks.
5. **CVSS 7.0 to 8.9 without an exploit**: the typical 30-day SLA.
6. **CVSS below 7.0**: regular patching cycles.

Two context signals refine this. **Fix availability**: where no fix exists, the severity is unchanged but the remediation shifts to documented acceptance, virtual patching, or a mitigating control. **In-use context**: an advanced scanner can correlate a CVE with runtime data to tell whether the vulnerable package is actually loaded and called, so a CVE in a library that never loads ranks below one on the hot path. (The full scoring model, CVSS/EPSS/KEV layering, lives in `vulnerability-management`.)

### CI/CD gate policy

Scanning is a gate, not a report. A defensible default:

- Block on CRITICAL CVEs with a public exploit.
- Warn on HIGH CVEs.
- Allow with a recorded exception where no fix is available and the risk is accepted.
- Block on any hardcoded secret, with no threshold; a leaked credential is always a fail.

## SBOM (Software Bill of Materials)

An SBOM is a machine-readable inventory of every component in an artefact. The common formats are SPDX (Linux Foundation) and CycloneDX (OWASP, more security-focused); SWID (an ISO standard) is less used for containers. SBOMs let you know exactly what is in an image, determine blast radius fast when a new CVE lands (which images contain the affected library?), meet regulatory requirements (US Executive Order 14028 mandates SBOMs for federal software), and track licence obligations.

```bash
# Generate a CycloneDX SBOM
trivy image --format cyclonedx --output sbom.cyclonedx.json myapp:v1.0.0

# Generate an SPDX SBOM
syft myapp:v1.0.0 -o spdx-json > sbom.spdx.json

# Query an SBOM for a specific package
jq '.components[] | select(.name == "log4j-core")' sbom.cyclonedx.json
```

## Supply-chain integrity

### SLSA

SLSA (Supply-chain Levels for Software Artifacts) grades build-integrity in ascending levels: provenance generated by the build system (L1), a build service that generates signed provenance (L2), a hardened and ephemeral build environment (L3), and all dependencies verified at L3 or higher (L4). Treat it as a maturity ladder for the pipeline rather than a single switch.

### Signing with cosign / Sigstore

Signing binds an image digest to an identity so a consumer can verify provenance before running it.

```bash
# Sign with a key
cosign sign --key cosign.key registry.example.com/myapp:v1.0.0

# Verify a signature
cosign verify --key cosign.pub registry.example.com/myapp:v1.0.0

# Keyless signing via OIDC (Sigstore Fulcio): no long-lived key to manage,
# the workload identity (for example a CI job) is the signer
cosign sign --identity-token "$ACTIONS_ID_TOKEN_REQUEST_TOKEN" \
  registry.example.com/myapp:v1.0.0

# Attach an SBOM to the image
cosign attach sbom --sbom sbom.spdx.json registry.example.com/myapp:v1.0.0
```

The pipeline signs; admission control enforces. The Kyverno `verifyImages` policy in `admission-control-examples.md` is what turns a signature into a hard gate at deployment time. Keep signing keys, or the OIDC identity configuration, in the secret store per `secrets-hygiene`; never commit a signing key.

## Runtime protection

Runtime security watches a running container for behaviour that a static scan cannot see. Typical detections: an unexpected shell spawned in a container, a binary that is not on the allowed list, sensitive-file access (`/etc/shadow`, SSH keys), outbound connections to unexpected destinations, container-escape attempts (namespace manipulation, dangerous syscalls), privilege-escalation attempts, and crypto-mining patterns. Open-source and commercial engines cover this (Falco is the common CNCF open-source option; platform vendors ship their own enforcers); the value is the behavioural model, not a specific product.

Two kernel controls reduce the runtime attack surface directly:

```yaml
# seccomp: restrict the syscalls a container may make
spec:
  securityContext:
    seccompProfile:
      type: RuntimeDefault        # the runtime's default profile
      # type: Localhost           # a custom node-local profile
      # localhostProfile: profiles/fine-grained.json
```

```yaml
# AppArmor: apply a mandatory-access-control profile to a container
metadata:
  annotations:
    container.apparmor.security.beta.kubernetes.io/my-container: runtime/default
```

## Secrets reaching a pod

This skill covers how a secret gets to a pod, not how the store itself is run (that is `hashicorp-vault-ops`) or the handling discipline (that is `secrets-hygiene`). The main patterns:

- **Native Kubernetes Secrets** are base64-encoded, not encrypted, in etcd by default. Enable etcd encryption at rest, restrict `get`/`list` by RBAC to only the pods that need them, and prefer a volume mount over an environment variable (an env var is visible to every process in the container).
- **External Secrets Operator** syncs from an external store (a cloud secrets manager or Vault) into Kubernetes Secrets on a refresh interval, so the source of truth stays outside the cluster.
- **Sealed Secrets** encrypt a secret with the cluster's public key so the sealed form is safe to commit to Git; the in-cluster controller decrypts it. This suits GitOps.
- **A Vault agent sidecar or the Vault Secrets Operator** injects secrets from HashiCorp Vault straight into the pod without a Kubernetes Secret in the path at all.

## Service-mesh mTLS

Inside a cluster, service-to-service traffic is plaintext unless something encrypts it, and any pod that the network policy allows can eavesdrop, with no cryptographic proof of who is calling. A service mesh (Istio, Linkerd) gives each sidecar proxy a cryptographic identity and enforces mutual TLS between services.

Under strict mTLS, every proxy holds an X.509 identity (a SPIFFE SVID), all service-to-service traffic is TLS-encrypted, the caller's identity is verifiable, and non-mTLS traffic is rejected.

```yaml
# Enable strict mTLS across the mesh
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system    # applies mesh-wide
spec:
  mtls:
    mode: STRICT

---
# Service-level authorisation on top of mTLS identity
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: allow-frontend-only
  namespace: my-app
spec:
  selector:
    matchLabels:
      app: backend
  action: ALLOW
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/my-app/sa/frontend"]
    to:
    - operation:
        methods: ["GET", "POST"]
        paths: ["/api/v1/*"]
```

### SPIFFE and SPIRE

SPIFFE (Secure Production Identity Framework for Everyone) defines a workload-identity standard; SPIRE (the SPIFFE Runtime Environment) issues the identities. A SPIFFE SVID is an X.509 certificate carrying a SPIFFE URI identity, issued to a workload after node and workload attestation. Istio, Envoy, and Consul use SPIFFE as their identity foundation, which enables cross-cluster and cross-cloud identity without static shared credentials.
