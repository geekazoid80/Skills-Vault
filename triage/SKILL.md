# Triage

Move issues on the project issue tracker through a small state machine of triage roles.

> **Skill marker**: When applying this skill, begin your reply with `[skill: triage]` on its own line so the transcript shows the skill fired. If multiple skills fire on the same reply, emit each marker on its own line at the top: transparency over neatness.

## Initial Assessment

If a `CLAUDE.md` or `AGENTS.md` exists in the working directory, read it first to understand the project's issue tracker, label vocabulary (especially how the canonical role names below map to actual labels), and any AI-attribution conventions before posting. Only ask the user for information not already covered.

Tracker handling:
- If the project uses GitHub, use `gh` for queries, label changes, and comments.
- If the project uses Linear, Jira, or another tracker with an MCP / CLI integration, use that.
- If no tracker integration is configured, present the triage decisions to the user for them to apply manually.

AI attribution: if the project has an AI-attribution convention (e.g. comments posted by an AI agent prefix with a disclaimer), apply it. The convention used in mattpocock's original triage skill is to prefix every triage comment and issue body with:

```
> *This was generated by AI during triage.*
```

Use this as the default if the project has no preference; check with the user if uncertain.

## Roles

Two **category** roles:

- `bug`: something is broken
- `enhancement`: new feature or improvement

Five **state** roles:

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on reporter for more information
- `ready-for-agent`: fully specified, ready for an AFK agent
- `ready-for-human`: needs human implementation
- `wontfix`: will not be actioned

Every triaged issue should carry exactly one category role and one state role. If state roles conflict, flag it and ask the maintainer before doing anything else.

These are canonical role names; the actual label strings used in the issue tracker may differ. The project should have configured the mapping in its CLAUDE.md or AGENTS.md; if not, ask the maintainer at first invocation.

### State transitions

An unlabelled issue normally goes to `needs-triage` first; from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time; flag transitions that look unusual and ask before proceeding.

## Invocation

The maintainer invokes triage and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42"
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

---

## Show what needs attention

Query the issue tracker and present three buckets, oldest first:

1. **Unlabelled**: never triaged.
2. **`needs-triage`**: evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes**: needs re-evaluation.

Show counts and a one-line summary per issue. Let the maintainer pick.

---

## Triage a specific issue

1. **Gather context.** Read the full issue (body, comments, labels, reporter, dates). Parse any prior triage notes so you don't re-ask resolved questions. Explore the codebase using the project's domain glossary, respecting ADRs in the area. If the project maintains an out-of-scope knowledge base (e.g. `.out-of-scope/*.md` files), read it and surface any prior rejection that resembles this issue.

2. **Recommend.** Tell the maintainer your category and state recommendation with reasoning, plus a brief codebase summary relevant to the issue. Wait for direction.

3. **Reproduce (bugs only).** Before any grilling, attempt reproduction: read the reporter's steps, trace the relevant code, run tests or commands. Report what happened: successful repro with code path, failed repro, or insufficient detail (a strong `needs-info` signal). A confirmed repro makes a much stronger agent brief.

4. **Grill (if needed).** If the issue needs fleshing out, run a grilling session (see the `grill-me` skill for the conversation pattern; capture findings as triage notes).

5. **Apply the outcome:**
   - `ready-for-agent`: post an agent brief comment (see "Agent brief" below).
   - `ready-for-human`: same structure as an agent brief, but note why it can't be delegated (judgment calls, external access, design decisions, manual testing).
   - `needs-info`: post triage notes (template below).
   - `wontfix` (bug): polite explanation, then close.
   - `wontfix` (enhancement): write to the project's out-of-scope knowledge base (if one exists), link to it from a comment, then close.
   - `needs-triage`: apply the role. Optional comment if there's partial progress.

## Quick state override

If the maintainer says "move #42 to ready-for-agent", trust them and apply the role directly. Confirm what you're about to do (role changes, comment, close), then act. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether they want to write an agent brief.

---

## Agent brief

When publishing an agent brief on a `ready-for-agent` issue, capture enough context that an AFK agent can pick the issue up cold. A durable agent brief includes:

- **What to build**: end-to-end behaviour, not layer-by-layer implementation.
- **Acceptance criteria**: a short bulleted checklist of observable outcomes.
- **Relevant code**: pointers to the modules / files that matter (avoid quoting code that may go stale).
- **Prior art**: any similar features or tests already in the codebase.
- **Out-of-scope**: what NOT to do.
- **Open questions** (if any): explicit, with the maintainer tagged.

If the issue was generated via `to-prd` and then sliced via `to-issues`, the slice body usually already contains enough; the agent brief comment can be a short pointer to the slice body plus any triage clarifications.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

---

## Resuming a previous session

If prior triage notes exist on the issue, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.

## Cross-references

- `to-prd`: PRDs published to the tracker land in `needs-triage` and get triaged through this skill.
- `to-issues`: vertical-slice issues land with `ready-for-agent` by default; triage handles them only if the slice needs re-evaluation.
- `systematic-debugging`: for bug reports, the Phase 1 / Phase 2 reproduction discipline is the same loop as the "Reproduce (bugs only)" step above; if reproduction is non-trivial, run the full systematic-debugging loop.
- `grill-me`: the grilling session for fleshing out an underspecified issue uses the grill-me conversation pattern.
- `subagent-delegation`: large `ready-for-agent` issues are good candidates for delegation to an AFK sub-agent.
